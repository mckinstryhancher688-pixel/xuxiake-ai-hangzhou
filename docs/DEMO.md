## 一、演示前的准备（只做一次）

| 项目 | 要求 | 怎么确认 |
| --- | --- | --- |
| 环境变量 | `.env.local` 里 8 个必填变量齐全（见 `.env.example`） | `GET /api/plan` 返回的账本里 `placeHourlyCap: 40`、`walkingHourlyCap: 80` |
| 高德 JS 凭据 | 已轮换 + 配了域名白名单 | **演示前必须确认**；未轮换时地图会退回手绘示意底图并标注「演示模式」 |
| 可写目录 | 进程对 `<项目>/.data/` 有写权限（双人协商快照落这里） | `node evidence/plan-guard-probe.mjs` 的 S9 项 |
| 每小时余量 | 冷核验单类约 36 次高德请求，其中步行 25 次；上限是步行 80 次/小时 | 演示当天如果同一小时里已经跑过两轮，第三轮会被上限拒绝——这是设计，不是故障 |
| 构建 | 演示用 `npm run build && npm start`，不要用 `next dev` | dev 模式热重载会重置进程内计数与缓存，等于每次都是冷跑 |
| 预热 | 代码改完、构建完、服务重启完，**最后**才做真实预热 | 顺序颠倒会白白多付一次冷核验（本项目踩过） |

一次演示消耗的预算（真实值，不是估算）：

- 冷核验：单类别约 36 次高德请求（POI 搜索 11 + 步行路径规划 25）；勾两个类别约 62 次（21 + 41）。
- 飞猪候选：每个类别 1 次 CLI 调用（上限 12 次/小时，缓存 10 分钟）。
- 百炼：每个「我到了」／「少走一点」／「让 AI 解释这次取舍」各 1 个回合（上限 40 回合/小时）。
- 双人协商本身：0 次新增调用。条件重解只在已实测的路段里挑；只有当你提交的硬条件需要一条**从没量过**的
  步行段时，界面才会弹出「同意新增 N 次高德实测」，不点就一次都不发。

## 二、一条固定的真实演示案例

这一条是推荐台上讲的那条，也是验收脚本里跑的那条。地点不写死在代码里——名字来自飞猪，
坐标与步行距离来自高德实测，所以具体站点每次可能不同，脚本只校验"链路成立"而不校验"必须出现某一站"。

### 单人半场（约 3 分半）

1. 打开 `http://localhost:3000`。默认勾选「自然风光」，首屏就能看到钉住的「生成我的路线」。
2. 点「生成我的路线」。服务端按勾选类别取飞猪候选，逐条与高德 POI 对名、取坐标、算步行段。
   这一步真实发约 36 次请求，界面右栏会显示进度。
3. 出结果后指着卡片上的三个标签讲：**谁给的**（飞猪／高德／产品设定）、**实测还是设定**。
   每站停留 30 分钟、缓冲 20 分钟、总预算 240 分钟这三项是设定值，界面上就写着"模拟"。
4. 点地图上的站 → 卡片跟着选中；点卡片 → 地图中心移到该站的**实测坐标**（偏差 0 米）。
   滚轮缩放、拖拽平移都操作一下，说明这些动作不会触发任何付费调用。
5. 点第一站卡片的「我到了」→ 百炼回合，返回现场讲解。回包里的每个"米／分钟"服务端都跟实测值对过账，
   对不上会在卡片上提示"需人工确认"，不会静默采信。
6. 点「少走一点」→ 智能体只能提"删哪几站"，服务端**重新逐段实测**后才允许上图。
   卡片显示"总行程缩短 X 米／Y 分钟"，这个差值是界面前后两份实测行程相减得来的。

### 双人协商（约 4 分钟，本项目的主打）

1. 出路线之后，右栏「双人协商」卡片点「发起双人协商（复用已实测数据，不新增高德调用）」。
   两条角色链接出现——强调一句：**链接就是这一方的身份**，服务端只存它的哈希。
2. 把「同伴那一份」链接用手机打开（同一 Wi-Fi 用 `-H 0.0.0.0` 起的地址，或现场直接投屏两个标签页）。
3. A 侧：步行上限填 4000 米，倾向选「少走路」，勾一处「必须去」，点
   「提交我的条件（已实测段内重解，不新增调用）」。
4. B 侧：步行上限填 3000 米，倾向选「多看几个」，勾另一处「必须去」，提交。
   右栏立刻出现真实差异（总步行前后两个数字、有符号的变化），以及逐条的 ✓／△ 清单。
5. 演示一次冲突（这是最出彩的地方）：B 把「必须去」勾成一个跟"≤3000 米"走不下来的站。
   界面出现「需要双方协商（硬约束互相矛盾，不会替谁放宽条件）」并给出证据行——
   系统不会偷偷放宽上限，也不会编一条走得通的路线。
6. 把 B 的步行上限改成 6000 米再提交 → 服务端重解出可行版本，双方各自点「确认 vN」。
   最后一方确认后，门禁卡片变绿：「正式执行：vN 已由双方确认」，地图、行程面板、
   「我到了」和百炼读的都是**同一份**双方确认版本。
7. 点「让 AI 解释这次取舍」。这是百炼唯一参与的地方：它只解释服务端已经算好的结论，
   不能改底线、不能编数字、不能替另一方同意。界面下方给出它建议的下一步动作，
   每个动作旁边写着服务端算出的「需新增 N 次高德实测」——数字由服务端回填，模型写不出新数字。
   百炼挂了的时候，卡片直接显示失败原因，规则求解结果原样保留，**不会拿固定文案冒充 AI 返回**。
8. 想再少走一点：单人界面的「少走一点」此时是灰的，提示「双方确认版不可被单人替换」；
   必须回到「双人协商」点「少走一点（只提提案，不改条件）」，提案要对方确认才生效。

## 三、电脑 + 手机完整验收步骤

分两批跑：**零付费批**可以随时重复，**真实服务批**每次消耗调用，只在代码与构建都定稿后跑。

### 零付费批（夹具／桩，不产生任何调用）

```bash
npm run build            # 先定稿代码
npm start &              # 真实可见的服务
npm run test:offline     # 68 + 22 + 24 + 25 = 139 项
node evidence/plan-guard-probe.mjs   # 12 项，只打本机端点
```

跑之前确认 `.data/plan-snapshot.json` 不存在或不含夹具方案（夹具套件会把快照写到临时目录，
但如果 `PLAN_SNAPSHOT_FILE` 被指到项目目录，开发实例会把夹具当成真实方案恢复出来）。

### 真实服务批（会花钱，一次跑完）

```bash
node evidence/plan-api-smoke.mjs    # 30 项：真实核验 → 双人闭环 → 门禁
node evidence/phase9-accept.mjs     # 30 项：双人真实浏览器（电脑 + 手机视口）
node evidence/phase8-accept.mjs     # 29 项：地图／刷新恢复／首屏／收益数字
node evidence/phase6-accept.mjs     # 25 项：真实地图与同步链路
node evidence/phase8-copy-probe.mjs #  7 项：文案与遮挡收尾探针，全程 0 次 POST
```

### 手工核对清单（脚本覆盖不到的观感）

电脑端（Chrome，1440×900）：

- [ ] 首屏不被任何弹窗挡住，地图瓦片画满，不是一片空白网格
- [ ] 三类来源标签在卡片上肉眼可见，"模拟"字样出现在停留时间与缓冲上
- [ ] 折线沿真实道路（不是两点直线），切换站点后所有站点仍在视野内
- [ ] 「生成我的路线」在右栏顶部固定；出路线后同一位置换成「我到了／少走一点」
- [ ] 双人协商的候选列表里**不出现英文枚举**（本轮修过一处：以前会印成「三潭印月-suspicious」，
      现在统一走中文口径「·可疑」「·开放时间待核实」）。这一处改动只有类型与构建背书，
      需要一次真实核验才能点到屏幕上——下次跑真实验收批时顺手勾掉
- [ ] 刷新页面：路线、讲解、到达记录原样回来，`/api/plan` 的计数一格没涨

手机端（390×844，真机或 DevTools 设备模式）：

- [ ] 「生成我的路线」贴在屏幕底部且在第一屏内，不被其他内容顶出视口
- [ ] 底部按钮条没有压住最后一段正文（滚到底能看到结尾）
- [ ] 层级正确：地图不盖住面板，面板不盖住按钮条
- [ ] 用同伴链接的 URL 打开，能看到「双人协商 · 你是 B」，且与电脑端 A 的状态同步

任一项不满足就停下修，不要在带缺陷的观感上录视频。
